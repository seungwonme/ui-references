# 재사용과 갤러리

## 기존 디자인으로 새 화면 만들기

1. 제공된 `DESIGN.md`, 토큰, 미리보기가 있으면 직접 읽는다. 항목을 찾아야 할 때만 `catalog`로 목적/플랫폼/정보 밀도가 맞는 항목을 고른다. 초안 비교가 필요할 때만 `--include-drafts`를 쓴다. 별도 제품에 제공 자료를 적용하는 일은 갤러리 설정이나 발행을 시작하지 않는다.
2. 대상 프로젝트의 기존 구현을 확인하고 핵심 작업, 콘텐츠 위계와 플랫폼 제약에 맞춰 화면 구조를 정한다. 웹/모바일/데스크톱 중 하나를 전역 기본값으로 삼지 않는다.
3. 원본의 글꼴, 의미 색상, 간격, 모서리, 상태와 컴포넌트 규칙을 대상 스택에 연결한다. 기존 컴포넌트 패키지를 쓸 경우 원본과의 차이를 확인하고 선택 이유를 기록한다.
4. 대표 화면 하나로 밀도/타이포그래피/합성/상태를 검증한 뒤 다른 화면으로 확장한다. 새로운 규칙은 원본에서 확인한 사실과 분리해 제안으로 남긴다.

레퍼런스가 여러 개면 섞을 역할을 명시한다. 글꼴/간격/표면을 항목마다 무작위로 조합해 하나의 화면에 적용하지 않는다.

원본 사진, 로고, 문구, 특정 화면의 배치는 재현을 요청받았거나 대상 콘텐츠에 필요한 경우에만 가져온다. 소재와 화면 구성을 자동 복사하면 대상 서비스의 목적보다 원본 장면이 앞서기 때문이다.

표면 효과는 사용 맥락과 함께 옮긴다. 글래스는 뒤의 콘텐츠가 비쳐야 하는 겹친 도구 모음이나 패널에 적용할 수 있다. 효과를 보여주기 위해 대상 서비스에 불필요한 배경 사진을 추가하지 않는다. 원본 충실도 비교는 해당 레퍼런스의 미리보기에서 수행한다.

## 갤러리 관리

`catalog`가 출력하는 목록을 갤러리의 입력으로 사용한다. 별도의 수동 목록에 제목/태그/경로를 복제하지 않는다. 이 명령은 목록 JSON만 만들며 화면/게시/배포를 수행하지 않는다.

갤러리에는 미리보기, DESIGN.md, 토큰, 출처/검증 범위로 이동하는 링크를 제공한다. 검색과 플랫폼/스타일 태그는 항목 메타데이터에서 만든다. 문서에 숫자로 나열한 토큰 표가 필요하면 토큰 파일에서 생성한다.

제목과 태그는 텍스트로 렌더링하고 메타데이터 문자열을 HTML로 실행하지 않는다.

갤러리 프레임워크와 빌드 방법은 저장소에 맞게 선택한다. CSS 클래스나 특정 컴포넌트 라이브러리를 스킬의 공통 규칙으로 고정하지 않는다.

기본 정적 빌더의 화면 구조는 [HTML 템플릿](../assets/gallery.html), [CSS](../assets/gallery.css), [검색과 필터](../assets/gallery.js)에서 생성한다. 저장소별 디자인은 갤러리 루트의 `gallery.css`로 덮어쓴다. 공개 항목의 생성된 토큰 CSS를 `@import url(...)`로 가져오고 `--g-*` 변수에 연결하면 숫자 값을 복제하지 않아도 된다. 폰트와 배경도 이미 공개 목록에 있는 파일만 상대 경로로 참조한다.

테마 파일은 저장소 소유이며 런타임 갱신으로 덮어쓰지 않는다. 새 파일 또는 수정본을 발행할 때 `publish`의 `--gallery-style <css-file>`을 사용한다. 스크립트는 이를 `gallery.css`로 저장하고 공개 경로/링크 검사, PR, Actions, Pages 검증을 함께 수행한다. 파일 안에는 공개해도 되는 스타일과 출처만 두고 사용자 환경값은 외부 설정 파일에 유지한다.

배경 URL은 `gallery.css`의 `body::before { background-image: url(...); }`에 적는다. CSS 변수에 넣은 상대 URL은 사용하는 스타일시트 기준으로 해석될 수 있으므로, 정적 링크 검사와 별도로 브라우저에서 실제 자산 로딩을 확인한다.

## GitHub Pages로 발행

1. 승인된 저장소와 공개 범위를 재사용한다. 아직 연결하지 않았으면 setup-gallery를 실행한다.
2. 자산/폰트/캡처의 재배포 조건과 개인 데이터를 검토하고 publication에 기록한다. 공개 가능한 파일을 publication.files에 명시한다. 원본 dump를 항목 전체 복사로 올리지 않는다.
3. `publish <entry-directory>`로 파일 목록과 대상을 확인한다. 이 기본 호출은 외부 변경을 하지 않는다.
4. 범위가 맞으면 `publish <entry-directory> --apply`를 실행한다. 스크립트는 원격 기본 브랜치에서 worktree를 만들고 공개 파일과 재현 가능한 빌더를 준비한 뒤 로컬 빌드, 커밋, 브랜치 push, PR 생성, CI 빌드 확인을 수행한다.
5. 리뷰 후 머지까지 이미 승인받았다면 같은 호출에 `--merge`를 붙인다. 이 옵션은 PR의 해당 commit 빌드가 성공했을 때만 머지한다. main의 Pages 배포 후 실제 사이트의 build.json commit이 merge commit과 같은지 확인한다.
6. 중단된 실행은 출력된 receipt와 PR을 읽고 `finish --pr <number> --apply`로 이어간다. 머지도 승인됐으면 `--merge`를 붙인다. 같은 항목을 새 PR로 중복 발행하지 않는다.

생성된 저장소에서는 `uv --no-config run --locked --script scripts/gallery.py build --output <new-empty-directory>`로 CI와 같은 빌드를 실행한다. 브라우저 검증은 이 산출물을 대상으로 한다. 검증 전 로컬 미리보기에는 build의 `--drafts`를 사용한다. 초안 표식을 붙이며 GitHub Actions 환경에서는 이 옵션을 거부한다. 래퍼는 프로젝트 스킬이 있으면 이를 우선 실행하고, 없으면 `.reference-ui/` 런타임을 실행한다. 버전과 hash는 `.reference-ui/bundle.json`에 기록하며 개인 스킬 경로를 참조하지 않는다. 생성 파일을 사용자가 수정했으면 자동 갱신을 멈추고 소유권을 확인한다.

스킬도 저장소와 함께 배포할 때는 첫 `publish`에 `--project-skill`을 추가한다. `.agents/skills/reference-ui-gallery`에 본문, references, scripts, assets, tests 전체를 생성하고 이후 발행에서도 함께 갱신한다. 전역 이름과 구분해 기존 설치와의 충돌을 피한다. 최초 Claude/GJC 연결은 사용 가능한 스킬 설치기의 프로젝트 설치 절차로 처리한다. 개인 설정과 다른 스킬은 포함하지 않는다.

Pages workflow는 PR에서 검증과 빌드를 하고 원격 기본 브랜치에서만 배포한다. 잠금 파일로 고정한 Python 환경과 공식 GitHub Actions를 사용한다. 빌더는 검토 완료 항목의 명시된 파일만 내보내고 링크, 경로 이탈, 로컬 경로, 자격증명 표식을 검사한다. 검사 통과가 시각 검증이나 재배포 권리 판단을 대신하지 않는다.

미리보기용 HTML 하나로 묶어 배포해도 디자인 시스템 정본 파일은 저장소에 유지한다. 네이티브 앱의 스크린샷/영상은 웹에서의 미리보기이며 네이티브 실행 검증으로 표시하지 않는다.
