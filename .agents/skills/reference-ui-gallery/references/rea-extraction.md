# REA로 UI 근거 추출하기

REA는 원본의 구조, 코드와 실행 관찰을 연결하는 분석 도구다. 디자인 시스템의 완성본을 자동 반환한다고 가정하지 않는다. 얻은 선언과 화면 측정을 `tokens.json`, `DESIGN.md`, `reference.json`으로 정리하는 일은 이 스킬이 맡는다.

## 도구를 고르는 기준

먼저 현재 하네스의 REA MCP 도구 목록과 선택한 도구의 입력 스키마를 읽는다. 아래 이름은 `rea` 서버의 호출명이며, 하네스가 다른 이름으로 노출하면 현재 목록의 동일한 기능을 사용한다. 이미 아는 파일이나 선택한 탭이 있으면 전체 환경 탐색부터 반복하지 않는다.

| 원본 | 첫 분석 경로 | 얻는 근거와 추가 확인 |
|---|---|---|
| 추출된 JavaScript 앱 또는 Electron ASAR | `mcp__rea__analyze_javascript_application`에 `input_path`, `format` 전달 | 모듈/진입점/참조/정적 관계. 관련 CSS, 폰트와 컴포넌트 파일을 좁혀 읽고 실제 렌더링과 비교한다. 앱 코드를 실행하는 도구가 아니다. |
| 앱 패키지나 압축 파일 | `mcp__rea__open_binary`로 정확한 파일 선택, `mcp__rea__inspect_artifact`로 목록 확인 | 필요한 파일을 찾고 실제 파일이 필요하면 `mcp__rea__extract_artifact`를 사용한다. 추출 위치는 반환값을 사용하며 원본 번들을 수정하지 않는다. |
| 실행 중인 웹페이지 | `mcp__rea__list_browser_targets`, `mcp__rea__inspect_web_page`, 필요한 경우 `mcp__rea__capture_web_screenshot` | 실제 loopback CDP endpoint와 조회된 `target_id`를 사용한다. DOM/접근성/리소스 근거를 읽고, 코드 관계가 필요할 때 `mcp__rea__analyze_web_bundle`을 추가한다. |
| 네이티브 Apple 앱 | 선택한 번들에서 `mcp__rea__inspect_asset_catalog`, `mcp__rea__decode_interface_builder`; 실행 화면은 `mcp__rea__observe_native_ui` | Assets.car 메타데이터, storyboard/nib 구조, 선택한 PID/window의 접근성/화면. 자산 목록 조회를 이미지 추출 성공으로 보고하지 않는다. |
| 스크린샷만 있음 | 이미지 관찰과 사용 가능한 브라우저/접근성 검사 | REA로 읽을 앱이나 탭이 없으면 바이너리 분석을 수행했다고 기록하지 않는다. 정확한 폰트, 숨은 상태, blur와 breakpoint는 미확인으로 남긴다. |

CDP 연결이 없는 사용자 브라우저의 UI 관찰은 사용 가능한 브라우저 스킬로 진행한다. REA를 쓰기 위해 사용자의 브라우저를 재시작하거나 인증 세션을 임의로 복제하지 않는다. 현재 작업의 질문에 필요한 코드와 화면만 조사한다.

## 실행 순서

1. 분석 질문과 조건을 고정한다. 예: 새 대화/사이드바의 글꼴, 간격, 표면 합성, 열린 메뉴 상태를 밝은/어두운 테마에서 확인한다.
2. 위 표에서 질문에 맞는 경로를 고른다. 정적 JavaScript 분석에 네이티브 디컴파일러를 먼저 설치하지 않는다.
3. REA 결과의 `evidence_id`, 원본 식별/버전, 소스 위치, coverage와 limitations를 보존한다. 정적 그래프에서 찾은 컴포넌트나 파일을 다음 조사 범위로 사용한다.
4. 관련 CSS 변수와 실제 컴포넌트의 font, color, spacing, radius, border, shadow, opacity와 상태 선언을 읽는다. 접근 가능한 웹 화면에서는 브라우저의 computed style과 element bounds로 실제 적용값을 대조한다. REA의 DOM/JavaScript 분석만으로 computed style을 측정했다고 쓰지 않는다.
5. 재현 화면을 같은 크기/테마/상태로 렌더링한다. 글래스는 blur 숫자뿐 아니라 뒤의 콘텐츠, 표면 불투명도와 레이어 순서를 비교한다.
6. 결과를 산출물 계약에 맞게 정리한다. 원본 선언, 렌더링 측정, 추정, 새 제안을 구분하고 새 화면에 재사용해 검증한다.

정적 앱 분석의 최소 입력 형태는 다음과 같다. 실제 호출 전에 현재 도구 스키마를 확인한다.

```json
{
  "input_path": "/absolute/path/to/extracted-app",
  "format": "directory"
}
```

ASAR 파일 자체가 입력이면 현재 스키마의 `asar` 형식을 사용한다. 분석 결과의 미해결 import, 동적 값, 인자에 의존하는 반환값은 화면의 실제 값으로 바꾸어 단정하지 않는다.

## 디자인 시스템으로 넘기기

| REA/브라우저 근거 | 보관 위치 | 기록 기준 |
|---|---|---|
| 선택한 원본, 버전, 분석 방법 | `reference.json`의 `sources` | 원본 제품/파일이 출처다. REA는 분석 방법이며 원본 디자인의 출처를 대신하지 않는다. |
| 필요한 선언, source locator, 제한 사항 | 항목의 `evidence/` 및 `reference.json`의 `evidence` | 원본 Evidence는 로컬에 보존하고 공개 파일에는 필요한 근거만 정리한다. 사용자 절대 경로나 인증정보를 옮기지 않는다. |
| 확인된 원시 값과 의미별 역할 | `tokens.json` | 직접 확인한 선언과 측정 조건을 설명하고 참조 관계를 보존한다. |
| 조합/상태/반응형/재질 사용 규칙 | `DESIGN.md` | 어느 조건에서 사용하는지와 원본에 없던 제안을 구분한다. |
| 화면 비교와 새 화면 실행 | 프로토타입과 검증 기록 | 파일 검사, 정적 분석, 실제 렌더링을 각각 수행한 수준으로 보고한다. |

REA의 confidence와 이 저장소의 근거 분류는 서로 다른 축이다. 예를 들어 파싱으로 얻은 선언은 관찰한 소스 사실이지만, 정적으로 추론한 호출 경로는 실제로 실행됐다는 증거가 아니다. `derived`라는 이유만으로 `measured`로 옮기지 않는다.

## 막혔을 때

- REA가 등록되지 않았으면 현재 설치된 CLI의 도움말과 공식 설치 문서를 확인한다. 사용할 수 없다면 직접 소스/브라우저/접근성 관찰로 진행하고 REA 미실행을 기록한다.
- 큰 번들이 한도에 걸리면 먼저 확인한 renderer/모듈/리소스 범위로 좁힌다. 잘린 결과를 전체 분석 완료로 표시하지 않는다.
- 네이티브 UI 권한이나 provider가 없으면 자원/정적 근거까지만 사용하고 실행 화면은 미검증으로 남긴다.
- 상태 전환이 필요하면 허용된 테스트 화면이나 합성 데이터로 검증한다. 캡처 도구의 성공을 실제 서비스 동작 검증으로 확대하지 않는다.

REA의 설치와 지원 범위는 공식 문서 및 현재 도구 스키마를 따른다. 도구를 바꿔도 근거와 한계를 남기는 계약은 유지한다.
