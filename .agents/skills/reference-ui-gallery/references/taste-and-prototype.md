# Taste와 prototype 적용하기

Taste는 시각 방향과 개선 판단에, Matt Pocock의 prototype은 비교 가능한 화면 실험에 사용한다. 원본 분석은 REA/브라우저가 맡고, 이 스킬은 그 결과를 대상 제품에 적용해 보관한다. 외부 스킬의 이름만 언급하고 사용한 것으로 기록하지 않는다.

## 적용할 스킬 선택

현재 하네스의 스킬 목록에서 아래 스킬을 찾아 본문을 읽는다. 설치 위치나 플러그인 버전을 문서의 절대 경로로 고정하지 않는다.

| 작업 | 사용할 경로 | 유지할 기준 |
|---|---|---|
| 원본 화면 재현과 디자인 시스템 추출 | REA/브라우저 + `mattpocock-skills:prototype`의 UI 비교 | 원본의 글꼴, 밀도, 선과 재질을 우선한다. Taste의 일반적인 금지 목록으로 원본을 바꾸지 않는다. |
| 레퍼런스가 없는 마케팅 사이트, 랜딩/제품 소개 페이지 | `taste-skill:design-taste-frontend`의 현재 기본 버전 + prototype | 제품의 실제 내용과 자산으로 방향을 정하고 구조가 다른 화면을 비교한다. |
| 기존 앱, 대시보드, 작업용 갤러리 개선 | `taste-skill:redesign-existing-projects`에서 대상에 맞는 진단 항목 선택 + prototype | 기존 스택과 토큰을 보존하며 위계, 밀도, 정렬, 상태, 포커스, 반응형을 개선한다. |
| 모바일 화면의 시각 콘셉트 이미지 | 요청 목적에 맞으면 `taste-skill:imagegen-frontend-mobile` | 콘셉트 이미지를 실제 앱 구현이나 원본 추출 근거로 표시하지 않는다. |
| 특정 미학이나 이전 버전 재현 | 사용자가 지목한 Taste 하위 스킬 | 호환성/스타일 목적을 먼저 기록한다. v1이나 특정 테마를 공통 기본값으로 바꾸지 않는다. |

현재 기본 Taste v2는 대시보드와 앱 화면을 적용 대상에서 제외한다. 글래스/얇은 테두리 금지나 이미지/모션 최소 개수도 웹 아트 디렉션의 규칙이다. 이 값을 서비스 화면의 공통 검사로 가져오지 않는다.

기존 앱 개선 스킬에도 사진, 폰트 교체나 장식 추가 권고가 있을 수 있다. 원본 레퍼런스의 확정된 규칙과 사용자 요구에 맞는 항목만 채택하고, 변경 이유를 기록한다. 원본이 특정 폰트를 쓰면 일반적인 폰트 금지 규칙만으로 교체하지 않는다.

## 웹 아트 디렉션에 Taste v2를 쓰는 순서

1. 대상, 사용자, 화면에서 할 일, 기존 스택, 고정된 색/서체와 실제 자산을 정리한다. 사진이나 로고가 필요하다는 사실을 원본 화면의 장식만 보고 추론하지 않는다.
2. 읽은 Taste 본문에 따라 현재 `draw.mjs`의 sector/section 목록을 확인하고 방향 후보를 받는다. 기본 스킬의 `--list sectors`, `--list roles`를 사용하며 전체 library를 컨텍스트에 복사하지 않는다.
3. 기존 디자인 시스템을 유지해야 하면 `--keep palette,type`으로 색과 서체를 고정한다. `--have`에는 실제로 있는 자산만 전달한다.
4. 제안된 방향을 제품 내용과 대조해 선택한다. 제안에 포함된 사진 세트도 자동 채택하지 않는다. 방향/seed, 선택 이유와 조정한 항목을 기록한다.
5. prototype 비교로 구조를 확인한 뒤, 선택한 화면에 Taste의 타이포그래피/구성/모션 절차를 적용한다. 기존 프로젝트의 스택을 바꾸라는 근거로 사용하지 않는다.
6. 적용 범위가 맞을 때 `lint.mjs`, `inspect.mjs`를 실행하고 실제 캡처를 열어 검수한다. 수치 검사 통과와 시각 품질 판단을 구분한다. 원본의 필수 규칙과 충돌하는 검사는 이유를 남기고 지원되는 개별 예외만 사용한다.

예: 기존 색/서체와 실제 제품 화면을 가진 개발 도구의 소개 페이지에서 방향 후보를 얻는다. `<taste-root>`는 현재 로드한 Taste 스킬 폴더다.

```sh
node "<taste-root>/scripts/draw.mjs" --sector dev-tool \
  --brief "실제 제품 화면으로 설명하는 개발 도구 소개 페이지" \
  --sections intro,showcase,faq,footer --have product-ui \
  --keep palette,type --options 3
```

선택한 방향은 같은 인자에서 `--options`를 빼고 `--direction <선택한-id>`로 구체화한다. 검사 명령의 현재 옵션은 설치된 본문과 스크립트 안내를 따른다. 이 절차를 앱/대시보드의 외형을 바꾸는 기본 절차로 호출하지 않는다.

## prototype을 공통 비교 절차로 쓰기

1. 답할 질문을 하나 적는다. 시각/구조 질문은 `prototype`의 `UI.md`, 상태 모델 질문은 `LOGIC.md`를 읽는다.
2. 기존 제품이면 실제 주변 UI와 데이터 밀도를 가진 화면에 변형을 배치한다. 독립 레퍼런스이면 해당 항목의 미리보기 안에서 비교한다.
3. 구조를 탐색할 때는 기본 세 안을 만든다. 정보 위계, 레이아웃과 주된 조작 방식이 달라야 한다. 색만 바꾼 세 화면은 비교안으로 보지 않는다.
4. 원본이 주어졌으면 A를 충실한 기준안으로 두고, 구조 탐색이 필요한 경우 B/C를 같은 디자인 문법으로 만든다. 재현만 요청한 경우에 불필요한 구조 변경을 추가하지 않는다.
5. 같은 입력/콘텐츠로 비교하고 URL의 `?variant=`와 눈에 띄는 선택기로 전환한다. 선택기 자체는 평가할 디자인 시스템과 구분하며 입력 중 키보드 조작을 가로채지 않는다.
6. 선택한 안과 이유를 기록하고 빈 상태, 로딩, 오류, 화면 크기 변화와 새 화면 재사용을 검증한다. 원본의 실제 데이터 변경 대신 합성 상태를 사용한다.

서비스의 프로덕션에는 검증한 결정을 반영한다. 이 갤러리는 프로토타입 자체를 보관하는 곳이므로 사용자가 요청한 비교안과 선택기를 공개 범위 검수 후 함께 보존한다. 일반 prototype의 임시 코드 정리 절차 때문에 승인된 갤러리 산출물을 지우지 않는다.

초기 탐색은 작은 구현으로 진행할 수 있다. 보관할 결과는 산출물 계약의 상태/반응형/접근성 검증을 거쳐야 하며, 단순히 실행된다는 이유로 `ready`를 표시하지 않는다.

## 결과와 미실행 기록

갤러리 패키지는 해당 항목의 `DESIGN.md`, 별도 제품은 그 제품의 기존 디자인 문서에 선택한 외부 스킬, 적용/제외한 규칙과 이유, 방향/variant 결정, 스택 선택 근거를 짧게 남긴다. 새 재사용 시스템에 문서가 필요할 때만 제품의 `DESIGN.md`를 만들며 사소한 수정에는 새 문서를 요구하지 않는다. 원본에 없던 결정은 `proposed`로 구분한다.

플러그인이 없으면 공식 저장소에서 현재 설치 방법을 확인한다. 설치하지 않고 진행할 때는 같은 비교 질문과 근거 계약으로 작업하되 Taste/prototype 스킬을 실행했다고 쓰지 않는다. 브라우저 검사를 못 했다면 해당 상태는 미검증으로 남긴다. 설치/발견, 스킬 읽기, 스크립트 실행, 실제 화면 검수는 각각 확인한 수준으로 보고한다.
